## 0. What this is, and what it is not

**The device run did not happen and is BLOCKED.**  This environment has no GPU (`nvidia-smi` absent; `raw/manifest.json` has `"gpu": {"devices": []}`) and the owner has
given no allocation or cap, which the protocol requires.  Nothing was rented, launched or called in any cloud.  Therefore:

* **There is no GPU measurement in this PR: no pairs per second on a device, no ratio to PS-3, no A/A or ABAB on a device, no speedup claim.**  The protocol's success
  condition (at least 50x PS-3 on one core) and stop condition (below 20x) are **not evaluated**; the requirement stays open.
* Every number below that comes from running something is a **CPU** number (a C emulation of the kernel on this host) or a **compile-time** number (the pinned `nvcc`/`ptxas`
  on the kernel source).  The two are labelled where they appear.
* The "expected ratio" the protocol leaves to be filled is **not filled: no device, no datasheet-sourced figure** (and the protocol's microbenchmark needs the device).  The blocker, what would unblock it and the next discriminating step are recorded in [`problems/pdp-ps5-gpu-device-run-blocked.md`](../../../problems/pdp-ps5-gpu-device-run-blocked.md).

What was done: PS-3's straight-line program (hash-frozen) was turned into CUDA code by an emitter, the same generated code was compiled as C and driven through the PS-0 verdict
corpus for `l = 8..12`, and the digests and root sets equal PS-0's.  Counted bit operations per pair were derived and cross-checked against the compiler's output.

## 2. What the kernel is

**The program.**  PS-3's program is the bit-sliced group-law pipeline for a batch of 8 *tasks* (PS-2 README section 5; `bspairs.rs` `batch`): per task the planes
`xu, yu, xv, yv` (a row's two points `U± = P₁ ± R`) and `x2, y2` (the partner base points), `6n` input planes per task, `n = 3l`; per task the outputs are a *hit mask*
(some candidate abscissa `x(U± ± P₂)` is below `2^l`) and an *exceptional mask* (a zero denominator).  Operations are `xor`, `and`, `or`, `not` and the fused `xand a b c = a ^ (b & c)`;
one Montgomery batch inversion per chain is shared by the 8 tasks.  The recorded program is hashed; its sizes are in 4.3.

**Mapping.**

| | |
|:--|:--|
| lane | bit `j` of a 32-bit word: one pair `(P_i1, P_i2)` |
| task | a row `i1` against a block of 32 consecutive partners `i2 = 32·blk + j` |
| job | 8 tasks of one row = 256 pairs = the work of one thread for one run of the program (one Montgomery batch) |
| grid | grid-stride loop over jobs; consecutive threads take consecutive jobs of the same row (the row values are read as a broadcast) |
| input planes | row planes: all-ones or all-zeros words from the row's four 64-bit values; partner planes: `n` words per block from a transposed table |
| output | per task `hit & valid & ~exc` and `exc & valid`; a non-empty pair is appended to a global list with one `atomicAdd` |
| host | confirms every hit lane and recomputes every exceptional lane with the exact group law, then forms the sorted roots `(x_i1, x_i2, t)` with `t < 2^l` |

`valid` is `i1 ≤ partner < m` (the pairs of the row): a job's lanes below the row's start, past the last base point, or in blocks past the table are masked.  The tiling is checked
(each of the `m(m+1)/2` pairs is covered exactly once, per rung, in every parity record: `tiling_covers_each_pair_once`).

**The emitter** (`pdp_ps5_emit.c`) reads `PROGRAM.slp` and its sidecar, recomputes the SHA-256 and refuses a mismatch, validates the program (operands refer to earlier wires, every
input once), and writes one statement per operation, `PS5_DEF(K, PS5_XAND(PS5_W(a), PS5_W(b), PS5_W(c)))`, in chunks, plus a header with `n`, `l`, the operation counts and the hash.
**Every program operation becomes exactly one `lop3`**: `xor` 0x3C, `and` 0xC0, `or` 0xFC, `not` 0x0F and the fused `xand` 0x78 (`a ^ (b & c)`, the "fusion" the program already
counts as one gate).  The emitter fuses nothing else; an XOR followed by an XOR that a three-input table could merge is left as two instructions (not attempted: the counted unit stays the program's gate count).

**Device form.**  Wires are single-assignment locals and gates are inline PTX `lop3.b32`.  `-DPS5_PLAIN_OPS` selects C operators instead (to compare what `ptxas` makes of them).

## 3. How the emulation relates to the kernel

| | device kernel | CPU emulation |
|:--|:--|:--|
| generated statements (`.inc`), wire numbering | same file | same file |
| job code: `ps5_job`, `ps5_valid`, input planes, record format | same source | same source |
| lop3 tables | PTX immediates `0x3c 0xc0 0xfc 0x0f 0x78` | same constants; `model` build evaluates each gate through `ps5_lop3(a,b,c,table)`; `plain` build uses the C operator |
| wire storage | locals, register-allocated by `ptxas` | one array; body split into chunk functions (`PS5_WIRES_IN_MEMORY`) |
| execution | a grid of threads, `atomicAdd` for the hit list | a loop over jobs on host threads, thread-private lists, merged and sorted by the driver |

*Why the array binding.*  During development the single-function device form was tried as C first: `gcc -O1` was stopped after more than 4 minutes and `clang -O2` after 2 minutes on the 65,000-statement
`l = 8` program (interactive probes; logs not retained).  Splitting the same statements into functions over a wire array, marking the chunk functions `noinline` and turning off dead-store elimination
(which dominated gcc's time on the array's stores) compiled the `l = 8` file in about 30 s (`plain`) or 57 s (`model`) in the same probes.  This is a storage binding, not a different program.

*Why `plain` is a faithful stand-in for `lop3`.*  `pdp_ps5_selftest` checks the five tables used against the C operators on all 8 input combinations (which determine a ternary function),
checks `ps5_lop3` against the definition (bit `4a+2b+c` of the table) for **all 256 tables**, and the `model` build runs the whole corpus through `ps5_lop3`.  What is **not** established: that
the hardware `lop3` implements the PTX definition the model transcribes.  The tables survive compilation (SASS `LOP3.LUT` with 0x78, 0x3c, 0xc0, 0xfc: section 4.4), which supports but does not prove it.

*What is not modelled:* instruction scheduling, registers, memory system, atomics' ordering (the list order differs on a device; the driver sorts it), warps and occupancy.

### 4.3 Counted bit operations per pair (derived; the arithmetic)

Definitions.  One program run is one thread's job: `G` gates, each one `lop3` on a 32-bit word = 32 lane operations, for `8 x 32 = 256` lane slots.  A "bit operation" is one gate on one lane (the plan's unit:
one 64-bit word XOR is 64).  "Fused" counts the xor-and gate as one operation (one `lop3`); "two-input" counts it as two.  `G` is read from the emitted program (`raw/emit/`), and equals the
exporter's `live_gates_fused` (PS-2/PS-3 records) for every rung.

1. bit operations per lane slot = `G x 32 / (8 x 32) = G / 8`, fused;  two-input: `(G + n_xand) / 8`.
2. `lop3` thread-instructions per lane slot = `G / 256`.
3. lane utilisation `u = m(m+1)/2 / lane slots per target` (lane slots = jobs x 256).  Per **valid** pair every figure is divided by `u`.

| 9 | 77,092 | 57,816 | 19,276 | 9,636.50 | 16,863.50 | 0.4961 | 19,424.8 | 33,992.6 | 607.02 |

*What the counts do not include:* forming the inputs (row broadcast, partner loads), valid masks and the hit list; the static SASS of the `l = 8` kernel has 70,976 instructions for 63,630 gates (section 4.4).  They are counts of the

would raise `u` for large `l`; not tried.  (Arithmetic only: the layout's ceiling is `u = 1`.)

The committed script now runs `nvcc -ptx` then `ptxas`; its flow was exercised once on `l = 8` with the `nvcc` front end replaced by a copy of the PTX the real `nvcc` made earlier (`raw/nvcc_l8_script_check_fake_nvcc_frontend.log`): `ptxas` on that PTX gave the same registers, stack and spills and the same SASS histogram as the first procedure (`raw/ptxas_l8_sm_80_from_ptx.txt`, `raw/sass_hist_l8_sm_80_from_ptx.txt`; 79.6 s).  That check does not exercise `nvcc -ptx` inside the script.

### 4.6 `l = 13` (optional)

### 4.7 Sanitizers and the one defect they found

`run_ps5.sh sanitize` builds the drivers (`pdp_ps5_parity.c`, `pdp_ps5_selftest.c`, the headers) with `-fsanitize=address,undefined -fno-sanitize-recover=undefined` against the existing, uninstrumented emulation object and runs them at `l = 8` (`raw/sanitizers_l8.txt`): the first run (commit `0577a7331` sources) stopped on a UBSan error, `memcpy` with a null destination for an empty hit list (`pdp_ps5_parity.c`), and LeakSanitizer reported unfreed buffers in both drivers.  Both were fixed (guard the copy; free the buffers) and every CPU result in this PR was regenerated from the fixed sources.  The final run: parity exit 0 and self-test exit 0, no sanitizer report.  The generated code itself was not sanitized.

## 5. Deviations, gaps and open requirements (all of them)

1. **Device run: BLOCKED** (no GPU, no allocation, no cap).  Items 6, 8, 9, 10 of section 1 stay open.  Nothing here supports or contradicts the 50x hypothesis.
2. **Expected ratio: not filled** (no device named, no datasheet-sourced figure, no device microbenchmark).
3. **Gray position per warp: dropped** as moot (item 3).  The hypothesis text names it; the kernel is the group-law program.
4. **Emulation binding:** wires in an array and chunked functions on the host; `plain` runs operators proved equal to the tables by exhaustive evaluation; hardware `lop3` semantics not verified here.  The device source was compiled, not run.
5. **Job layout wastes lanes** (`u = 0.25 ... 0.87`, table in 4.3) because a job is 8 blocks of one row; counted per valid pair accordingly.  Cross-row jobs not tried.
6. **Register pressure:** the `l = 8` kernel uses 255 registers and spills (4.2').  No tuning (blocking, fewer live inputs) was attempted.
7. **Exceptional lanes** never occur in the PS-0 corpus; the host's exact recomputation of an exceptional lane was not exercised (the kernel's exceptional mask was, by the self-test).  The driver does not handle degenerate targets (none in the corpus).
8. **No `fes_gpu.rs` bridge, no NVRTC path** (the body is an `#include` of a generated file; an NVRTC build would concatenate it), **no CI job**.  `fes_gpu.rs` is untouched.
9. **`l = 14, 15, 16`: not attempted** (exporter limit `n <= 39`).
10. Per-rung program hashes for `l = 8..12` are PS-2's; the `l = 13` program's hash is first recorded here.
11. CPU timings are from a shared host and are exploratory; the host differs from PS-0..PS-3's first host (same CPU family, 2.10 GHz vs 2.80 GHz).

## 7. Commands (exact) and files

Run from the repository root; the lock is the shared benchmark lock (`/tmp/crypto-bench.lock`) through `crypto`'s `tools/isolated_bench.py busy --wait` (this repository's `scripts/isolated_bench.py` is the same tool).

```sh
# the PS-3 binary of the crypto repository exports the programs (SHA-256 c40434d6...a6c1; run_ps5.sh hash-checks every program it exports)
export PDP_SPEEDUP=/tmp/ps3_bin/pdp_speedup OUT=/tmp/pdp_ps5_build
PS5=experiments/pdp-oracle-speedup-20261011/ps5/run_ps5.sh
LOCK="python3 tools/isolated_bench.py busy --wait --"      # this repository's scripts/isolated_bench.py is the same tool
$LOCK $PS5 build plain                                       # export + emit + build, l = 8..12
for L in 8 9 10 11 12; do $LOCK $PS5 selftest $L 50 plain; $LOCK $PS5 parity $L 3 plain; done
$LOCK $PS5 sanitize                                          # ASan + UBSan on the drivers at l = 8
PS5_RUNGS=13 $LOCK $PS5 build plain; $LOCK $PS5 selftest 13 50 plain; $LOCK $PS5 parity 13 3 plain
$LOCK $PS5 build model                                       # every gate through the lop3 model
for L in 8 9 10 11 12; do $LOCK $PS5 selftest $L 20 model; $LOCK $PS5 parity $L 3 model; done
$PS5 manifest                                                # hardware, tools, hashes of sources and binaries
# compile check of the CUDA source (needs nvcc: ecc2k130/scripts/fetch_cuda.sh DIR; no device is used)
NVCC=DIR/bin/nvcc NVDISASM=nvdisasm $PS5 nvcc 11
# graph and PDF (matplotlib and typst in a virtual environment)
python3 experiments/pdp-oracle-speedup-20261011/ps5/plot_ps5.py && python3 experiments/pdp-oracle-speedup-20261011/ps5/render_report.py
```

Files: `suite/cuda/pdp_ps5_{device.cuh,kernel.cu,emulate.c,emit.c,slp.h,host.h,parity.c,selftest.c}`, `suite/cuda/build_pdp_ps5.sh`; here `programs/` (the six sidecars and the hash list; the programs themselves are regenerated), `corpus/` (PS-0's five corpora, byte-identical to
`crypto` commit `e33ec00a3`, hashes in `SHA256SUMS`; the PS-3 `l = 13` sample), `expected_digests_ps0.txt`, `raw/`, `figures/`, `report/`.
