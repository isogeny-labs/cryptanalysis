# n = 83 field-ops-2 producer with native work counted

**Status (2026-11-08): counting producer derived and verified locally on
one point and seed per base (D4, M38). No counted band on a receipt yet.
No timing claims.** `[pcc:unverified]`

## Why

AGENTS.md section 5a prices every arm's unpriced native work at 0, 0.1 and
1 GAE per operation against the matched rho. The rho reference `rT` already
counts its own work (`charges_setup_and_solve`). The field-ops producers
emit no operation counts, so
`../koblitz-n83-k4c400-20261107/band_model.py` *models* the IC units. It
takes the per-probe and per-attempt composition of the archived counted
run 39882571652, which counted the **stacked** producer
(`../koblitz-n83-opcounts-20261023`), and applies it to the field-ops
producer's measured probe and attempt counts. This experiment counts the
field-ops-2 producer itself.

| `test_opcounts2.py` | derivation tests: inverse, committed output, every edit only adds counting or counted calls, nothing is written unless enabled. Also tests of the band script (unit composition, refusal of uncounted processes, a band from a synthetic receipt). |
| `verify/` | local verification outputs and the `cargo test` log (no timings). |

Counting is opt in twice over:

- Without the Cargo feature `op-counts`, `bump` is an empty inline function.
- With the feature, counters are written only when the process runs with
  `KIC_OPCOUNTS=1`. Without it, the summary and target record have exactly
  the parent's keys (no `op_counts`).

The counting binary is a separate counting pass and never a timed arm.
Counters are global relaxed atomics, and reads are taken outside every
timed interval. Kinds, classes and phases are the opcounts experiment's (24
kinds, `ic-op-counts/v1`), so its `band.py` prices them unchanged. The sites
are listed in the derivation's docstring. Three of them are new to this
lineage:

- each regular frame candidate counts one `s3_root_solve`. Its two partner
  words x(T_s ± R_k) are that pair's S3 roots, formed from a shared
  inversion. With s ≠ 0 it also counts 2 `frobenius_x`.
- `frame_root_xy` counts one `ec_lift_x` (a point's y from its x, two per
  frame state).
- `lift_linear_lanes8` counts 8 canonicalizations.

The field kinds are reported, not priced. The products and squares made
inside an inversion are taken back out, following the opcounts convention.

## How to build and run

```
# crypto 770f6a69 restored at ../koblitz-n83-fieldops2-20261107/snapshots/r770 (that experiment's restore.py)
python3 make_counted2_source.py --check
cd online-c && cargo build --release --locked --features op-counts
python3 ../local_verify.py --parent ../target/release/ic_online_fieldops2_r770 \
    --counted ../target/release/ic_online_fieldops2_counted_r770      # D4 and M38, s000, 3 repeats
python3 ../counted_band.py --counts ../verify/counts.jsonl --out-dir ../verify/compare_model --compare-model
# with a receipt and a full counting pass over its points:
python3 ../counted_band.py --receipt-dir <panel> --counts <counts.jsonl> --out-dir <out>
```

## Local verification (2026-11-08, cloud-agent VM, CPU 3, nice 19)

The point is k4c400's `s000`. The rank process uses kD4FO / kM38FO with
seed 2501. The cold process uses cD4FO / cM38FO with seed 7 and the base's
frozen factor-log table. Each configuration was run by three binaries:

- the parent, `ic_online_fieldops2_r770`, sha256 `1cc0897c...`;
- the counting binary without `KIC_OPCOUNTS`, sha256 `6da2861d...`;
- the counting binary with `KIC_OPCOUNTS=1`, three times.

Results, all in [`verify/local_verify.json`](verify/local_verify.json):

- **Gates.** Every run passes the k4c400 `arm.check` gates against its base
  (index and layout digests, closure shape, frozen table, rank = K'). The
  rank processes write the base's frozen factor-log table.
- **Outputs and digests.** Counting off and counting on both produce the
  parent's summary (70 keys) and target record (33 keys) with timing,
  hardware-counter and RSS fields removed (`op_counts` too, when on).
  The digests are unchanged: D4 `logical_states_blake3` 4fe91f10...,
  M38 092515809717....
- **Reproducibility.** The counts are identical across the three counting
  runs of every process.
- **Probes.** Counted rank-stage probes are the producer's own count plus
  one re-lookup per resolved hit. D4: 16,991,268 counted vs 16,991,264
  reported. The cold target's counted probes equal the producer's
  (D4 3,352,716).
- **Tests.** `cargo test` of the counted source (fieldops2 and opcounts2
  modules) passes with counting off and with `KIC_OPCOUNTS=1`
  ([`verify/cargo-test-opcounts2.txt`](verify/cargo-test-opcounts2.txt)).

### Counted vs modelled (one point, one seed per base)

The model is `band_model.py`'s, evaluated on the same producer quantities:
probes, attempts, K' and table entries. The IC unit is the rank process's
rank stage plus the cold process's setup, linear algebra and target (the
`analyze_v2.py` unit). Full per-kind table:
[`verify/compare_model/counted_band.md`](verify/compare_model/counted_band.md).

| base | group ops counted / model | unpriced native ops counted / model | ratio |
|---|---:|---:|---:|
| D4 | 784 / 841.0 | 102,707,200 / 74,504,241 | 1.379 |
| M38 | 2,809 / 2,859.4 | 209,757,116 / 146,729,738 | 1.430 |

The model **under-states the unpriced native work by 38% (D4) and 43%
(M38)**. Its group operations are close: 0.93 and 0.98 of counted. Where
the gap comes from, read off the per-kind table:

- **Index build.** The cold process's setup builds the index:
  33.2 M (D4) and 76.8 M (M38) unpriced operations, mostly S3 solves and
  canonicalizations of every stored state's roots. The model only charges
  table entries for setup.
- **Per-probe work.** Canonicalizations and S3 solves come out at 1.6 to
  1.75 times the model, and `frobenius_x` at 1.8 to 2.0 times.
- **Frame candidates.** The new frame candidates add `ec_lift_x`
  (102,362 and 221,002), which the stacked composition has none of.
- **Exact or close kinds.** Root-index probes and relation lifts match by
  construction. Inserts are within 5%: counted inserts are attempts, the
  model uses distinct entries.

These are single-point, single-seed counts. A band needs a counting pass
over a receipt's points.
