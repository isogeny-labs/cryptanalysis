# Evidence review: 15-position prime-norm scalar radix

**Question.** Does the `268−τ` prime-norm radix provide a verified 15-position integer recoding, and what does the existing paired panel establish against the 16-position `190−τ` format?

**Scope and method.** This report audits the frozen artifacts in this directory; it does not run a new benchmark. The search enumerated the declared `T=240…320` prime-norm candidates, checked selector/radius/terminal bounds, compared the six-candidate selector with the bounded global search on all sign-canonical residues, and replayed the selected recoding. Integer checks are complemented by independent affine point replay and native full-residue/holdout tests. The performance comparison uses panel `2481bd3c0f7e491698694ccb039f1048` on RunPod instance `thyvmdqmzsz5ik`, comparing radix 15 (`N=71,023`) against radix 16 (`N=35,533`) on the same 128 frozen scalar inputs. No secp256k1 curve identity or subgroup claim is needed for the scalar-format comparison; the independent group replay is specifically over secp256k1.

The generic runner's archived `summary.json` is retained unchanged. Its `paired_speedup` value (1.003080) is the median from the pre-comparison A/A calibration case, and its generic `speedup_claim_eligible=false` describes that runner-level aggregate. The radix comparison result is separately derived by `analyze_tier1.py` from the `compare` case after checking both adjacent A/A calibration cases; the comparison median and interval are in `tier1-analysis.json`. The two summaries describe different calculations and must not be conflated.

The 96 raw arm receipts record child user/system CPU time, wall/online time, cgroup throttling and memory-event deltas, steal time, faults, and context switches. The audit found zero throttling, steal, major faults, or OOM events; involuntary context switches total 647 across all arms. The receipts do not retain the runner's per-child peak RSS field. The preflight records a 1,781,030,912-byte cgroup peak, but that is container-wide and cannot stand in for per-process peak RSS. Thus the frozen panel passes the comparison's service gate, while its retained data do not satisfy the repository's complete per-run memory-evidence requirement. Reconstructing that missing process statistic from the other counters is not valid.

The panel manifest records hashes for both benchmark binaries and source files. However, the candidate overlay requires a parent source snapshot whose hash (`e195374c…`) does not match the source file committed in the base tree; the manifest's external `/workspace/bench-sources/…` snapshots are not present in the run archive or this review workspace. The PR preserves the overlay procedure and hashes, but that historical native build cannot be reconstructed from the checked-out evidence alone. The input fixture itself is preserved in the base experiment tree and its SHA-256 matches the panel manifest.

## Limitations and open checks

The paired interval describes repetition variation on one cloud instance, not host-exclusive performance or variability across providers, CPUs, or scalar distributions. CPU affinity records process placement only. One-call latency was not measured. Table construction, preparation, and memory favor the 16-position reference. The formal proof covers the integer recoding; the curve-specific group bridge is supported by independent bounded replays but remains a formalization gap. These results do not establish production integration or end-to-end secp256k1 library speedup.

The exact source for the measured binaries is bound by the recorded source hashes and native overlay receipts; the raw panel archive contains the run receipts, while the PR preserves the overlay and source-generation scripts. Reproducing the historical remote allocation is not part of this review and no new performance run was performed.
