# Native PairIndex dual x bitmap M31 comparison

Question: does the two-projection filter that improved the standalone Rust explicit-pair collector also improve the library's actual `PairIndex` pipeline? The target and subgroup are frozen in `m31-integrated-local-screen/fresh-public.json`, SHA-256 `dc724fc613d9c2b824b90d59c876f1f7f84b3273d8d607c648e1ba3fbc089252`. Use all five public Q, interval factor base B384, m=2, 64 lanes, pair chunk 64, four million query and five-second online bounds, and a fresh `m31-fast` child process per arm. The same public P, Q and walk seed pair each arm. No target scalar is supplied to the solver. The wrapper independently checks every reported answer by public generator multiplication.

Build three Rust variants from one source commit: `current20` is the existing 128 KiB multiplicatively mapped bitmap; `high22` uses direct high 22 x bits in a 512 KiB bitmap; `dual22` adds a direct low 22-bit bitmap (1 MiB total) and requires both bits before HashMap lookup. The exact HashMap, pair generation, witnesses, curve arithmetic, walk and elimination are otherwise unchanged. Include the archived C++ rho on the same Q as a distance control. Require each solved Rust arm to match exact answer, work counts, pair counts and certificate content; independently replay all certificates. Preserve incomplete, invalid, timed out and failed arms, including wall and CPU cost. A missing answer never becomes a timing win.

`SEEDS.json` (SHA-256 `2032a7176fc8a4569084724556c63fe95a8d8b9e5d4ff5789dafe477fe056b6b`) freezes the three walk seeds, schedule seed and exact SHA-256 derivation. Run all five targets x three seeds, 15 paired four-arm blocks, shuffled with the declared Python 3.13.1 MT19937 schedule seed. Rotate arm order by `(target_id + seed_index) mod 4` so each arm occupies multiple positions. The target set is fixed and public; seeds are independent walk streams but do not make new problem instances.

Wall and parent-plus-child CPU clocks begin before child launch and end after output parse and independent generator verification. The Rust internal `cold_to_report_ns` measures from main entry through serialization preparation, including basis generation, pair-index build, online collection, elimination and certificate checks. Save phase timings, all stdout/stderr, exact source/binary/input hashes, CPU and hardware manifest, and raw rows. Compilation and frozen-source loading precede timing; OS caches are not flushed. Record a local gain only if `dual22` beats both `current20` and `high22` in at least 12/15 valid matched blocks and by median paired wall and CPU ratio at least 1.05, with answers and workload identity intact. Otherwise retain the negative result. This local screen does not meet isolated Tier 1 or independently signed PCC standing; any general speed claim needs those separate gates.

The filter correctness argument is the conjunction of two necessary x-membership bits and the existing exact-index lookup. `m31-dual-x-bitmap/DualBitmap.lean` proves first successful payload preservation under the support invariant. The native Rust index invariants and certificate replay must be tested independently; Lean is not used to prove timing.
