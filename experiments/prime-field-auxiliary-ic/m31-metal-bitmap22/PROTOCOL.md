# Frozen 20-bit versus 22-bit Metal bitmap M31 comparison

Frozen before timed outcomes on 2026-11-27. The fixed admission at Q0 with seed 2911332506172719186 is excluded from this panel. It checked complete-certificate and work parity but its timings are not comparable because shader compilation cache state differed by arm order.

Question: Does a 22-bit multiplicative x bitmap reduce false-positive GPU candidates enough to improve full cold same-target four-summand M31 index-calculus solves beyond the merged 20-bit Metal path?

Both arms use curve `y²=x³+2x+14` over `p=2147483647`, subgroup order `2147505293`, generator `(1,814455902)`, interval B195, m4, 64 walk lanes, chunk 16384, max 100000 queries, 5 s online cap, and the same Rust PairIndex witness table. The five frozen public coordinates are Q0 `(1767503692,244402461)`, Q1 `(686106551,2137700595)`, Q2 `(949616523,2050168716)`, Q3 `(1568678311,615355077)`, Q4 `(2146214436,1536824028)`. No target scalar enters either solver. Arm 20 uses the merged 20-bit bitmap and its exact GPU screen; arm 22 changes only the bitmap width, CPU bitmap query and GPU hash shift. Both use the same source, compiler flags and complete Rust certificate path.

Seed derivation: SHA-256 of ASCII `m31-metal-bitmap22/v1`, NUL, 16 raw master bytes, NUL, ASCII label; take first 8 bytes big endian and mask to 63 bits. Master `6a7ede564247af0ea2ae8356e6adf3c4`; `walk/0..2` produce `6921442232125326734`, `2985729302292425937`, `3510290430897429259`; `schedule` produces `2104417048374113301`. Python 3 `random.Random(schedule).shuffle` orders 15 target/seed blocks, with arm order alternating 20-first and 22-first across shuffled blocks. Each block pairs the same public target and walk seed; seeds are independent across the three replicates.

Build the Rust library, Swift dylib and experiment executable once from the frozen PR commit with `rustc -O`/`swiftc -O`; record commit and SHA-256 of source files, binary, shader and runner in a manifest before outcomes. Compile before timing. Run every arm as a fresh process; charge process launch and exit, basis and pair-index construction, bitmap construction and upload, shader loading/compilation, GPU dispatch/wait/transfer, exact CPU witness checks, relation collection, elimination and certificate replay. Record process wall from before launch through exit, and child user+system CPU from `resource.getrusage(RUSAGE_CHILDREN)` deltas. OS caches are not flushed. Preserve all stdout/stderr, exit codes, failures and timeouts.

For each of 15 pairs require identical target, seed, scalar, complete-field certificate digest, query count, relation count and rank. Independently verify every scalar by public affine group multiplication. A local performance gain requires all 30 arms to complete correctly, median paired 20/22 wall and child CPU ratios each ≥1.15, and at least 12/15 22-bit wins on both metrics. Report paired ratios, absolute wall/CPU, bitmap positives, all failures and the matched rho distance separately. This is producer-run evidence until independent PCC standing; measured timestamps are never Lean proof obligations. `MetalScreen.lean`'s generic bitmap invariant applies to either width, but compiled shader/FFI refinement remains open.
