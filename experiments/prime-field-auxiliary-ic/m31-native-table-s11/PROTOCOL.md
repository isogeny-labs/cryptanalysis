# Frozen native table and larger-basis M31 screen

Status: protocol frozen before implementation or timing. Public p=2^31-1 curve, generator, target and auxiliary/plain factor-base construction are the exact source and fixtures used by `m31-basis-sweep/replay.py`; the checked public scalar is 123456789. The 500-point bases reproduce the archived fixtures, while the 1,013-point auxiliary basis is the full s=11 chain lift and the plain control is its first 1,013 accepted x values. These are two different collector workloads; compare exact workload identity only within the same basis and size.

Question: can native Mersenne field arithmetic in the pair-table builder, combined with the already measured fused native candidate scan, repay the larger auxiliary basis's 45.7 ms table build and 16.5 ms elimination costs? The s=11 cold charged wall baseline is about 151 ms, versus about 78 ms for s=10. A candidate must beat the **500-point current full-pipeline control**, not merely its own 1,013-point Rust counterpart, to count as an algorithmic performance lead. The first screen uses the same public target only; it cannot establish a general exponent result.

The C++ row builder receives validated canonical coordinates and Rust-owned scratch/output buffers. It computes one row of ordinary affine sums using `m31_batch_inverse` and scalar Mersenne multiplication/subtraction, emitting exact x,y coordinates. Equal-x entries emit a sentinel and are resolved with the Rust group law. Rust retains the exact table insertion order and first payload, reflected-row rule, bitmap, walk, relation checks, elimination and answer verification. The fused collector scan accepts either 500 or 1,013 pairs and preserves ascending signed index order, with exceptional denominators falling back to Rust.

Before timing: (1) run the existing 1,097,730-output inverse ABI checker; (2) independently compare every native row output with Python group addition on representative rows including equal-x and identity cases for both bases/sizes; (3) compare byte-identical complete sorted `(point key, first payload)` maps and matching entry counts for Rust and native table builds; (4) run full Rust audit builds that compare native and Rust first exact hits at every walk state, verify every relation and independently multiply the reported scalar by the generator. Any mismatch aborts timing and is retained.

Timed arms per block: for each basis (auxiliary/plain) and size (500/1013), compare three configurations: current Rust table and Rust collector, native table with Rust collector, and native table with fused native collector. Use seeds 0,1,2 and four balanced order rounds, shuffled by `random.Random(2026112507)`: 48 three-arm blocks, 144 fresh-process arms. Charge wall and parent-plus-child CPU from before basis regeneration/input writing through table build, relation collection, elimination, answer check, output parsing and process exit. Compilation and audit checks precede timing. Do not flush OS caches. Preserve per-arm raw CSV with phase timings, trials, relations, entries, native calls/fallbacks, and input digest. Within each basis/size/seed/round, require equal answer, trial count, relation count, entry count, basis digest and exact table map.

Report paired wall and CPU ratios and wins for each intervention and the cold 500-versus-1013 comparison, including all failures/censors. A promising result requires a separately frozen fresh-seed confirmation and matched same-target rho before any crossover claim. Existing Lean field and bitmap proofs do not establish C++ ABI refinement or runtime. Do not turn measured timestamp arithmetic into a Lean theorem.
